# HTTP/1.1 vs HTTP/2 vs HTTP/3 — Multiplexing, HPACK, and Why the Transport Changed

## 1. Why does this exist?

HTTP/1.1 (RFC 9110/9112, the current spec family, having obsoleted RFC 7230-7235) was designed for a web of independent, small requests. Modern pages and APIs fire dozens of concurrent requests per origin, and HTTP/1.1's model turned out to have real, structural bottlenecks under that load — bottlenecks that couldn't be fixed by tweaking HTTP/1.1 itself, because they were baked into how it used TCP. HTTP/2 (RFC 9113) and HTTP/3 (RFC 9114) are successive redesigns of *how requests are framed and multiplexed*, each solving the previous version's specific structural problem, and each worth understanding as a direct response to a named, mechanical limitation — not as an arbitrary "newer is better" upgrade.

## 2. Mental model

HTTP/1.1 is one phone line per conversation — if you want to talk about five things at once, you need five phone lines (five TCP connections), each paying its own handshake and slow-start cost (Lesson 2). HTTP/2 is one phone line with the ability to interleave five conversations on it, tagged by conversation ID (streams) — cheaper to set up, but if that one physical line has a problem (a lost packet), *all five conversations* stall until it's fixed, because they're all riding the same ordered TCP byte stream underneath. HTTP/3 keeps the "one connection, many conversations" idea, but replaces the underlying phone line with something where each conversation has its own independent thread that a single bad patch of the line doesn't disturb.

## 3. Simple explanation

- **HTTP/1.1**: text-based, one request in flight per TCP connection at a time (pipelining exists in the spec but is essentially unused/unsupported in practice due to head-of-line blocking at the *application* level — if request 1's response is slow, request 2's response, even if ready, must wait behind it). Browsers work around this by opening multiple parallel TCP connections per origin (historically 6 per host).
- **HTTP/2**: binary framing, single TCP connection per origin, true request **multiplexing** — many logical streams interleaved over that one connection, no application-level head-of-line blocking. But it inherits **TCP's** head-of-line blocking (Lesson 2): if one TCP segment is lost, the kernel withholds *all* subsequent bytes on that connection from the application until the loss is retransmitted and arrives in order — even though those bytes may belong to a completely unrelated, otherwise-ready stream.
- **HTTP/3**: same multiplexing idea as HTTP/2, but running over **QUIC** (RFC 9000) instead of TCP. QUIC is built on UDP (Lesson 3) and implements its own reliability *per stream*, so a lost packet only blocks the specific stream it belonged to — other streams on the same connection keep flowing.

## 4. Technical explanation

**HTTP/1.1's specific costs:**
- Headers are re-sent, uncompressed, on every single request — for API traffic with repetitive headers (auth tokens, cookies, `User-Agent`, `Accept`), this is real, wasted bytes on every request.
- One request/response in flight at a time per connection (in practice — pipelining is a dead feature). Browsers/clients compensate with connection parallelism, which multiplies handshake (TCP + TLS) cost across connections rather than amortizing it.

**HTTP/2's mechanisms (RFC 9113):**
- **Binary framing layer**: requests and responses are broken into typed, length-prefixed **frames** — the frame types defined in RFC 9113 §6 include `DATA` (message body), `HEADERS` (header fields, opens/continues a stream), `PRIORITY` (deprioritized/deprecated in this revision — see below), `RST_STREAM` (abruptly terminate a single stream without killing the connection), `SETTINGS` (connection-level configuration), `PUSH_PROMISE` (server push — see below), `PING` (liveness/RTT measurement), `GOAWAY` (graceful connection shutdown, telling the peer the highest stream ID it will still process), `WINDOW_UPDATE` (flow control), and `CONTINUATION` (for header blocks too large for one frame).
- **Streams**: each request/response exchange is a **stream**, identified by an ID, and many streams are interleaved as frames on the single underlying TCP connection — this is what "multiplexing" concretely means: frames from stream 1, stream 3, and stream 5 can be physically interleaved on the wire and reassembled by ID on the other end.
- **HPACK (RFC 7541)**: HTTP/2's header-compression scheme, purpose-built (a general compressor like gzip was avoided specifically because it enabled the CRIME/BREACH class of compression-oracle attacks against TLS). HPACK combines: a **static table** of ~61 common header field name/value pairs (e.g., `:method: GET`) that both sides already agree on and never need to transmit, a **dynamic table** that both peers build up incrementally as a connection progresses — a header sent once can be referenced by a short index on subsequent requests instead of being re-sent in full — and **Huffman coding** for literal values that aren't in either table. The practical effect: repetitive request headers across many requests on the same connection shrink dramatically after the first request.
- **Stream prioritization**: HTTP/2 originally (RFC 7540) shipped a dependency-tree-based prioritization scheme letting a client hint "stream 5 depends on stream 3" and assign relative weights. **RFC 9113 formally deprecates this scheme** — in practice it turned out to be complex, inconsistently implemented across servers/proxies, and often ignored or actively worked around; newer prioritization approaches (e.g., the simpler urgency-based scheme in RFC 9218) have superseded it.
- **Server push (`PUSH_PROMISE`)**: allowed a server to proactively send a response the client hadn't asked for yet (e.g., push `style.css` when the client requests `index.html`, anticipating it'll be needed). In practice this has been **widely removed** from major implementations (Chrome removed it) because it was hard to get real cache-awareness right — servers often pushed resources the client already had cached, wasting bandwidth — and HTTP/103 Early Hints emerged as a preferred, simpler alternative for the same "tell the client what's coming" goal.
- **TCP head-of-line blocking, inherited**: this is HTTP/2's real, unfixable-within-TCP limitation. Because all streams share one ordered TCP byte stream, a single lost packet stalls the kernel's delivery of every byte after it to the application — including bytes belonging to streams that had nothing to do with the lost packet. On a lossy network (mobile, Wi-Fi), this can make HTTP/2 perform *worse* than HTTP/1.1's multiple parallel connections, because loss on the one shared connection now blocks everything instead of just one of several independent connections.

**HTTP/3's mechanisms (RFC 9114, over QUIC — RFC 9000/9001/9002):**
- **QUIC replaces TCP+TLS as the transport**, running over UDP. It reimplements TCP's reliability and congestion control itself (RFC 9002 defines QUIC's loss detection and congestion control, using a CUBIC- or BBR-like approach — Lesson 2's congestion-control content applies conceptually, just implemented in userspace/library code atop UDP instead of in the kernel's TCP stack), but critically, **per stream** — each QUIC stream is an independently reliable, ordered byte sequence, so a lost packet carrying stream A's data only stalls stream A; streams B, C, D continue delivering to the application uninterrupted. This directly and structurally fixes HTTP/2's inherited TCP head-of-line-blocking problem.
- **TLS 1.3 is integrated into QUIC's handshake itself** (RFC 9001), not layered on top afterward — QUIC's connection establishment *is* a TLS 1.3 handshake, meaning connection setup and encryption setup happen together in a way that gets QUIC down to effectively **1 RTT for a new connection** (matching TLS 1.3's improvement over TLS 1.2, but now also folding in what used to be a separate TCP handshake) and **0-RTT for resumption** (same mechanism and same idempotency caveat as Lesson 6's TLS 1.3 0-RTT).
- **Connection migration**: a QUIC connection is identified by a **connection ID**, not by the traditional TCP 4-tuple (source IP, source port, dest IP, dest port). This means a client that changes network (e.g., a phone switching from Wi-Fi to cellular mid-request) can keep the *same* QUIC connection alive across that IP change, without a full reconnect — something structurally impossible for TCP, whose connection identity is tied to the IP/port tuple that just changed. This is a genuinely new capability, not just a performance tweak.
- **No head-of-line blocking at the transport layer, by construction** — this is the headline result of the per-stream design above.

## 5. How it works internally

An HTTP/2 stream's frames are interleaved on the wire but each frame carries its stream ID in its header — the receiving endpoint's HTTP/2 layer demultiplexes frames back into per-stream buffers before handing completed messages up to the application, exactly analogous to how TCP itself demultiplexes packets to sockets by port (Lesson 2), just one layer higher and finer-grained. QUIC does something structurally different: because it owns its own loss recovery per stream (rather than delegating to a single ordered TCP byte-stream), the receiving QUIC implementation can deliver stream A's completed, in-order bytes to the application the moment they're ready, without waiting on stream B's outstanding retransmission — there's no shared ordering constraint across streams the way there structurally is in a single TCP connection.

## 6. Example

```
curl -v --http2 https://api.github.com    # negotiate HTTP/2 explicitly (ALPN-based negotiation)
curl -v --http3 https://cloudflare.com    # if your curl build supports it — HTTP/3 negotiated via QUIC
```
Browser DevTools' Network tab shows a "Protocol" column (`h2`, `h3`, `http/1.1`) per request — a fast, direct way to see which transport a real production API is actually using, and to notice that different requests to different origins on the same page can be using different protocol versions simultaneously.

## 7. Code

Node's `http2` module exposes multiplexed streams directly, making the "many streams, one connection" model concrete instead of abstract:
```js
import { connect } from 'node:http2';

const client = connect('https://api.github.com');

// Two requests fired concurrently over the SAME underlying connection —
// no second TCP/TLS handshake, unlike two http.request() calls under HTTP/1.1.
for (const path of ['/users/octocat', '/repos/nodejs/node']) {
  const req = client.request({ ':path': path });
  req.on('response', (headers) => console.log(path, headers[':status']));
  req.end();
}
```

## 8. Failure scenarios

- **HTTP/2 over a lossy network genuinely underperforming HTTP/1.1**: a documented, real phenomenon on mobile/Wi-Fi links with meaningful packet loss — TCP head-of-line blocking on the single shared connection can be worse than the independent-connection-per-request degradation HTTP/1.1 has. This is a legitimate, evidence-based reason some mobile-heavy services adopt HTTP/3 specifically, not just following a trend.
- **Misconfigured intermediary stripping ALPN or forcing HTTP/1.1 downgrade**: a corporate proxy or older load balancer that doesn't understand HTTP/2 can silently force a downgrade, and if your monitoring assumes HTTP/2 performance characteristics, this shows up as an unexplained regression for a subset of traffic.
- **UDP being blocked or throttled by restrictive network middleboxes**: because HTTP/3 rides on UDP, some corporate firewalls or overly aggressive traffic-shaping equipment block or deprioritize it, causing clients to fall back to HTTP/2 — real HTTP/3 deployments need a TCP/HTTP-2 fallback path for exactly this reason, not as a theoretical concern.

## 9. Common misconceptions

- **"HTTP/2 solved head-of-line blocking."** It solved *application-level* head-of-line blocking (multiple requests no longer queue behind each other in your code's model of the world) but explicitly did not and could not solve *transport-level* head-of-line blocking, because it still rides on a single ordered TCP stream. This distinction is precisely why HTTP/3 exists as a separate, transport-level redesign rather than an HTTP/2 patch.
- **"HTTP/3 is just HTTP/2 but faster."** It's HTTP/2's multiplexing semantics preserved, on top of a genuinely different transport (QUIC/UDP instead of TCP) that removes a structural limitation HTTP/2 could not remove on its own.
- **"More concurrent HTTP/1.1 connections is basically equivalent to HTTP/2 multiplexing."** No — each of those parallel connections pays its own independent TCP handshake, TLS handshake, and slow-start ramp-up (Lessons 2 and 6); HTTP/2 pays those costs once and reuses the warmed-up connection for everything.

## 10. Trade-offs

HTTP/2's single-connection model trades "many independent connections, no shared-fate risk, but repeated setup cost" for "one connection, amortized setup cost, but shared-fate risk under packet loss." HTTP/3 largely resolves that specific trade-off by removing the shared-fate risk, but at the cost of running its own transport/congestion-control stack in user space rather than relying on decades of kernel-level TCP optimization, and at the cost of needing UDP to actually reach the destination unimpeded — not a universal guarantee across all networks even today.

## 11. Real-world applications

- Major CDNs (Cloudflare, Fastly, Google) and browsers have broad HTTP/3 support today; API gateways and load balancers (Lesson 8) increasingly support terminating HTTP/3 from clients and speaking HTTP/1.1 or HTTP/2 to backend services — meaning your NestJS server itself may never need to speak HTTP/3 directly even when your public-facing API effectively supports it, because termination happens at the edge.
- Connection migration (QUIC) is directly relevant to any mobile-heavy API — a user's connection surviving a Wi-Fi-to-cellular handoff without a full request retry is a concrete, user-visible reliability improvement, not a theoretical one.

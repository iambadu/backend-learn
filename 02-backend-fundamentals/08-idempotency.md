# Idempotency — Making "Retry It" Safe

## 1. Why does this exist?

Module 1 established that networks lose, duplicate, and delay packets, and that TCP's reliability guarantees stop at "the bytes I sent arrived" — they say nothing about whether the *client* actually received confirmation that they arrived. A client that times out waiting for a response has no way to know whether the request never reached the server, reached it and failed, or reached it and **succeeded**, with only the response getting lost on the way back. Retrying is the obvious client-side response to a timeout — but for a non-idempotent operation (Module 1, Lesson 5: `POST /payments` has no built-in idempotency guarantee), a naive retry of a request that actually already succeeded creates a duplicate side effect. This lesson is about making retries safe *by design*, not by hoping timeouts don't happen.

## 2. Mental model

An idempotency key is a receipt number you write on a form before mailing it, and keep a copy of. If the response never comes back and you're not sure whether the original made it, you don't fill out a new form — you resend the *same* form with the *same* receipt number, and whoever's processing it recognizes the receipt number and either tells you "already handled, here's what happened" or safely processes it for the first time — but never processes the same receipt number twice.

## 3. Simple explanation

An **idempotency key** is a unique value, generated by the *client*, sent alongside a request (conventionally in an `Idempotency-Key` header — this exact header name and pattern comes from Stripe's API, which effectively established the industry convention). The server stores this key together with the outcome of the first request it's associated with. If the same key arrives again — because the client is retrying after a timeout, not because it's intentionally repeating the operation — the server recognizes it and returns the **stored result of the original request**, without re-executing the underlying operation a second time.

## 4. Technical explanation

**This is a different, stronger guarantee than HTTP method idempotency (Module 1, Lesson 5), and the distinction matters:** `PUT`'s idempotency is a *contractual* property of the method — "replacing a resource with the same payload twice has the same end state" — but that's a statement about the *resulting resource state*, not about whether a *side effect* (like sending exactly one payment-confirmation email, or charging a card exactly once) happens exactly once. An idempotency key gives you the latter, much stronger guarantee, deliberately, for operations (like `POST /payments`) where the HTTP method itself provides no such guarantee at all.

**How the mechanism actually needs to work, precisely (this is where naive implementations get it wrong):**
1. Client generates a unique key (Stripe recommends a V4 UUID or any random string with sufficient entropy to make accidental collision practically impossible) — generated *once per logical operation*, not once per HTTP request attempt; the whole point is that retries of the same logical operation reuse the same key.
2. Client sends the request with `Idempotency-Key: <key>`.
3. Server, **before** executing the underlying operation, checks whether this key has been seen before. If not, it proceeds, and — critically — **atomically** records "this key is now in progress" as part of the same transaction that performs the operation (Level 3's transaction content becomes directly load-bearing here: a race between two concurrent requests carrying the same key, arriving near-simultaneously due to a client retrying slightly too early, must not both pass the "have I seen this key" check before either records it).
4. Server stores the **full result** (status code and response body) of the first execution, keyed by the idempotency key.
5. If the same key arrives again — whether the client is genuinely retrying after a lost response, or a network intermediary duplicated the request — the server returns the **stored, original result** directly, without re-executing the operation.
6. **A safety check often missed**: the server should verify the *request parameters* accompanying a repeated key match the original request's parameters, and reject (rather than silently reusing the stored result, or worse, silently re-executing) if they don't — this guards against a client bug reusing a key for what is actually a genuinely different operation, which would otherwise silently return the wrong stored result.

**Idempotency keys are not meant to be permanent** — Stripe's own documented approach recycles keys after roughly 24 hours, treating the mechanism as protection against near-term retry duplication (the realistic window in which a client might legitimately retry after a timeout), not as a permanent, indefinite record of every operation ever attempted (that's what your actual audit log, Level 10/11, is for — a distinct concern from idempotency).

**Where the "already in progress" state matters — the concurrent-retry race, made concrete:** imagine a client's request genuinely reaches the server and begins processing (say, calling out to a payment provider, Project 2), but the client's timeout fires *before* that processing completes, and the client retries with the same key while the *original* request is still in flight. A correct implementation must recognize "this key is already being processed" and either make the second request wait for the first to finish (then return its result), or reject it outright — rather than allowing two concurrent executions of the same logical operation to both proceed because neither one had yet written a "completed" record when the other checked. This is precisely why "check the key, then execute, then store the result" as three separate, non-atomic steps is insufficient — the check-and-mark-in-progress step needs the same atomicity discipline Lesson 6 (rate limiting) needed for its distributed counter check, for exactly the same underlying reason: a race window between check and write.

**Where idempotency keys should live, architecturally, so they survive exactly the failure they're meant to protect against:** the stored key-to-result mapping needs to be durable and consistent with the operation's own effects — typically written in the **same database transaction** as the operation itself (Level 3's ACID content becomes directly relevant: if the operation commits but the idempotency record doesn't, or vice versa, you've reintroduced exactly the duplicate-or-lost-effect problem the whole mechanism exists to prevent).

## 5. How it works internally

A payment-creation endpoint backed by PostgreSQL: the handler begins a transaction, attempts to `INSERT` a row into an `idempotency_keys` table with a `UNIQUE` constraint on the key column *and* the actual payment record, in the same transaction. If the `INSERT` on the idempotency table fails due to the unique constraint (meaning this key was already used), the transaction rolls back the attempted new payment entirely, and the handler instead reads and returns the previously stored result for that key. This leans on the database's own uniqueness/transaction guarantees (Level 3) to get the atomicity this lesson requires, rather than trying to build that atomicity manually in application code.

## 6. Example

```
curl -X POST https://api.example.com/payments \
  -H "Idempotency-Key: 8f14e45f-ceea-467e-a927-fdb0ee9a1e51" \
  -d '{"amount": 5000, "currency": "usd"}'
```
Send this exact request twice, deliberately — a correctly implemented API returns the identical response (including, notably, the same resource ID) both times, and a check against your payments table confirms only one payment record was actually created.

## 7. Code

```ts
async function createPayment(idempotencyKey: string, params: PaymentParams) {
  return db.transaction(async (tx) => {
    const existing = await tx.query(
      `SELECT response_body, status_code FROM idempotency_keys WHERE key = $1`,
      [idempotencyKey],
    );
    if (existing.rows.length > 0) {
      return existing.rows[0]; // return the ORIGINAL result, do not re-execute
    }

    const payment = await tx.query(
      `INSERT INTO payments (amount, currency) VALUES ($1, $2) RETURNING *`,
      [params.amount, params.currency],
    );

    // UNIQUE constraint on `key` makes a concurrent duplicate INSERT fail
    // and roll back this entire transaction — the race window is closed
    // by the database's own transactional guarantee, not application logic.
    await tx.query(
      `INSERT INTO idempotency_keys (key, response_body, status_code) VALUES ($1, $2, 200)`,
      [idempotencyKey, JSON.stringify(payment.rows[0])],
    );

    return payment.rows[0];
  });
}
```

## 8. Failure scenarios

- **Generating a new idempotency key on every retry attempt** — completely defeats the mechanism; this is a real, common client-side mistake (the key must be generated once per *logical* operation and reused across retries of that same operation, not regenerated per HTTP attempt).
- **Storing the idempotency record and executing the operation as two separate, non-transactional writes** — a crash between the two leaves the system in exactly the ambiguous state the mechanism exists to eliminate: did the operation happen or not?
- **Reusing a key across genuinely different request parameters without detecting the mismatch** — silently returns a stale, wrong result for what the client believes is a new operation.
- **No expiry on stored keys** — unbounded growth of the idempotency-key table, and (a subtler issue) a key becoming eligible for legitimate reuse in a *new*, unrelated operation far in the future getting incorrectly treated as a duplicate of the old one.

## 9. Common misconceptions

- **"Making an endpoint idempotent means using PUT instead of POST."** Method-level idempotency (Module 1, Lesson 5) is a weaker, structural property about resource *state*; idempotency-key-based idempotency is a deliberate, explicit mechanism guaranteeing a specific side effect happens at most once — they solve related but distinct problems, and `POST` endpoints (payment creation being the canonical example) very much can and should be made idempotent via keys even though `POST` itself carries no such guarantee.
- **"Idempotency keys prevent all duplicate payments."** They prevent duplicates caused by *retries of the same client-initiated request* — they do nothing about a user double-clicking "pay" and generating two genuinely distinct requests with two distinct keys, which is a UI/UX problem, not an idempotency-key problem.
- **"This is only relevant for payment APIs."** It's relevant for any operation with a real-world side effect that must not be duplicated — sending an email, provisioning a resource, decrementing inventory — payments are simply the domain where the cost of getting it wrong is most viscerally obvious.

## 10. Trade-offs

Idempotency keys add real implementation cost (a storage table, transactional discipline, a TTL/cleanup policy, request-parameter matching logic) in exchange for making retries — which Module 1 establishes are an unavoidable fact of unreliable networks — genuinely safe for non-idempotent operations. Skipping this for anything with a real side effect isn't a simplification; it's accepting duplicate-side-effect risk as a live possibility in production.

## 11. Real-world applications
